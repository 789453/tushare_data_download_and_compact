## 2. 四个域的字段，我基于 `feature_registry.csv` 的专业读取与解释

我本地读取了 `feature_registry.csv`，它一共 40 个特征，恰好是 5 个域 × 每域 8 个特征。你当前真正准备用于 AlphaPROBE 的是 A/B/C/E 四个域；D 域在 registry 里存在，但 `allow_in_alphaprobe=0`，更像模型侧或风格侧变量，而不是当前因子搜索变量。这个设计是合理的。

下面我按域讲，不只列字段，还讲这些字段在工程里应该如何使用。

***

### 2.1 A 域：`feature_A_price_volume`

A 域 8 个特征是：

- `ret_cc_1d`
- `ret_oc_1d`
- `gap_open`
- `intraday_range`
- `upper_shadow_ratio`
- `lower_shadow_ratio`
- `turnover_free`
- `volume_ratio_ln`

registry 显示，它们的来源主要是 `daily` 和 `daily_basic`，语义是“**标准化后的量价行为摘要**”，不是原始 open/high/low/close 直接暴露给表达式。\
这正符合你想要的方向：**用你自己的 Tushare feature，而不是沿用 qlib 的原始 OCHLV+VWAP 变量空间。**

但这里最重要的不是字段名，而是两个事实。

第一，A 域的公式本身是合理的：\
`ret_cc_1d = close/pre_close - 1`、`gap_open = open/pre_close - 1`、`intraday_range = (high-low)/(pre_close+eps)`、`turnover_free = turnover_rate_f / 100`、`volume_ratio_ln = log(1+volume_ratio)`。\
这意味着 A 域从“经济语义”角度是可以直接进入 AlphaPROBE 的。

第二，A 域当前**值质量并不完全稳健**。\
`feature_data_submit.json` 里已经暴露出两个明显问题：

- `ret_oc_1d` 的上界达到 `1279.0`
- `lower_shadow_ratio` 的下界达到 `-22000026.70`

这两个范围都已经超出了正常金融比率字段的可接受范围。尤其 `lower_shadow_ratio` 理论上应在 `[0,1]` 附近，出现千万级负值，只可能是分母 `(high-low)` 接近 0、价格字段不一致、或异常日口径错位导致的。`ret_oc_1d` 上界 1279 也说明 `(close/open-1)` 这个比率在某些样本上遭遇了接近零的 `open`、复权口径错配、或脏值。相比之下，`ret_cc_1d`、`gap_open`、`intraday_range`、`upper_shadow_ratio`、`turnover_free`、`volume_ratio_ln` 的范围虽然有尾部，但至少统计形态是“金融上能解释”的。

所以 A 域的工程建议不是“整个域不用”，而是：

- **保留 A 域作为正式挖掘域**
- 但把 `ret_oc_1d` 与 `lower_shadow_ratio` 设为 **quarantine feature**
- 在进入 AlphaPROBE 变量注册前先做字段级 QA
- 若 QA 未通过，就不进入当前实验的变量 token 列表

这一点非常重要：\
你说算子不改，我赞成；但**变量能否被注册到表达式系统里**，必须由 QA 决定，而不是只看 registry 里的 `allow_in_alphaprobe=1`。

***

### 2.2 B 域：`feature_B_moneyflow`

B 域 8 个特征是：

- `imb_sm_amt`
- `imb_md_amt`
- `imb_lg_amt`
- `imb_elg_amt`
- `net_mf_to_amount`
- `large_buy_share`
- `large_sell_share`
- `flow_divergence`

这是你当前四个域里**最稳、最适合最先启动**的域。原因有三点。

第一，数据起始时间长，从 2010 年开始。\
第二，缺失率几乎全为 0。\
第三，绝大多数变量天生就是**已经良好归一化的比例型变量**：四个不平衡度都严格在 `[-1,1]` 附近，`large_buy_share` / `large_sell_share` 在 `[0,1]`，`flow_divergence` 在 `[-2,2]`。这意味着它们非常适合直接作为 AlphaPROBE 的变量 token，而不需要额外做复杂标准化。唯一需要特别小心的是 `net_mf_to_amount`，registry 和 json 都写了“Note unit conversion needed”，这不是注释而已，而是工程风险提示：如果 `net_mf_amount` 和 `amount` 在单位上不一致，这个比率会整体偏离。

所以 B 域的设计原则应该是：

- **B 域是主力启动域**
- 不改算子，只改变量注册
- 保留 registry 中已有的 fill 策略：`zero_if_both_zero_else_nan`、`nan_if_amount_zero`
- 增加一条域级 QA：确认 `net_mf_amount` 与 `amount` 的单位一致，否则整列停用
- B 域不需要先做额外截面 zscore 后再挖，因为其变量本身已经是比率型、边界型

换句话说，B 域是你整个 AlphaPROBE 新方案的**最佳 baseline 域**。\
如果我要排试运行顺序，第一优先级就是 B。

***

### 2.3 C 域：`feature_C_chip`

C 域 8 个特征是：

- `close_vs_cost50`
- `close_vs_weight_avg`
- `chip_width_95_5`
- `chip_width_85_15`
- `overhang_95`
- `support_5`
- `winner_rate_pct`
- `price_pos_hist`

从 registry 看，这个域的公式设计是非常漂亮的：\
不是直接暴露 `cost_50pct`、`cost_95pct` 这些原始成本价位，而是用**相对 close 的结构特征**。这正是筹码数据最合理的工程化方式。

但 C 域当前有一个非常大的隐患：\
一些值范围已经提示出**价格口径可能不一致**，或者在某些样本上出现了近零价格分母问题。例如：

- `close_vs_cost50` 最小到 `-18.86`
- `close_vs_weight_avg` 最小到 `-12.08`
- `chip_width_85_15` 最大到 `31.51`
- `support_5` 最小到 `-5.56`

如果公式真的是 `(close - cost)/close` 或 `(cost_85 - cost_15)/close`，这些极值并非完全不可能，但已经大到足以怀疑两个问题：

1. `close` 与 `cost_*` 使用了不同复权口径；
2. 个别样本 `close` 极小，导致比例爆炸。

这类问题在筹码数据里尤其危险，因为它不是“单个异常点会影响一点点”，而是会直接把表达式搜索空间带歪。举例说，如果某些样本里 `chip_width_85_15` 经常出现 10 倍、20 倍、30 倍，搜索算法会错误地把它当成一个极强非线性信号，而实际上它可能只是口径错位。`winner_rate_pct` 和 `price_pos_hist` 的范围是干净的 `[0,1]`，这说明 C 域内部不是整体坏，而是“**某些价差比率列有口径一致性风险**”。

所以 C 域不是不能用，而是必须带着下面这套工程约束：

- C 域只从 2018 年起跑，不能强行和 A/B/E 用同一段超长历史做统一搜索
- 在进入 AlphaPROBE 之前，先做“close 与 cyq price scale consistency check”
- 若 `abs(close_vs_cost50) > 3`、`abs(close_vs_weight_avg) > 3`、`chip_width_85_15 > 5` 这类样本占比明显异常，则优先回到原始 `cyq_perf` 和 `daily` 重算，而不是直接信现有比率列
- 即便保留现列，也应在域级预处理里加入 `robust_winsor + invalid_sample_flag`
- `winner_rate_pct` 与 `price_pos_hist` 可优先保留，因为它们边界清晰、解释性强、统计更稳

我的判断是：\
C 域依然值得挖，而且很可能能出有辨识度的因子；但它比 B 域更依赖**前置 QA 和口径统一**。

***

### 2.4 E 域：`feature_E_intraday_summary`

E 域 8 个特征是：

- `hour1_ret`
- `lasthour_ret`
- `midday_reversal`
- `intraday_trend_eff`
- `hourly_volatility`
- `volume_concentration_pm`
- `vwap_close_bias_1h`
- `high_low_time_skew`

从设计思想看，这是一个非常好的域：\
它不是把 60 分钟 bar 全量丢进去，而是先压缩成日级的日内行为摘要。对个人研究和算力控制来说，这条路线非常正确。

但是 E 域当前的值质量问题比 A 域还尖锐，主要有四个：

- `lasthour_ret` 的最大值在 json 中是 `null`
- `volume_concentration_pm` 的最小值是 `-2.0958`
- `vwap_close_bias_1h` 的最小值是 `-971.79`
- `intraday_trend_eff` 的取值严格打满在 `[-20,20]`

其中，`volume_concentration_pm = vol_pm / vol_total` 理论上不可能小于 0；`vwap_close_bias_1h = (close - vwap_1h) / close` 理论上也不应该低于 -1 太多，更不可能到 -971；这说明 E 域里至少有两个字段——`volume_concentration_pm` 和 `vwap_close_bias_1h`——不是“尾部厚”这么简单，而是**公式与原始口径不匹配**。`intraday_trend_eff` 明显被 clip 到了 `[-20,20]`，这不是坏事，但意味着它在搜索时已经不是纯原始统计量，而是带硬截断的变量；`lasthour_ret` 最大值为 null 说明统计摘要输出里可能存在不完整的 summary 过程。

所以 E 域的工程策略应当是：

- **保留域，不保留所有列**
- `hour1_ret`、`midday_reversal`、`hourly_volatility`、`high_low_time_skew` 可以进入第一批
- `intraday_trend_eff` 可以进入，但要在 registry 里明确“已 clip”
- `volume_concentration_pm`、`vwap_close_bias_1h` 先停用，要求回到 60min 原始表重算
- `lasthour_ret` 需要先查 summary 生成逻辑是否在 max 统计上漏了非空过滤

这一点也再次说明：\
**你当前最需要改的不是 operator，而是 feature admission gate。**
