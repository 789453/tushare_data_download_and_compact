这份特征设计的方向是对的，域拆分也清晰，但当前 JSON 里已经出现了几类**不能靠普通 winsorize 掩盖**的问题：一类是**系统性缺失/对齐问题**，一类是**分母设计导致的爆值与符号穿透**，一类是**本应有自然边界的比例变量越界**，还有一类是**工具函数层面的面板泄露风险**。这些问题如果不先在数据处理层解决，后面不管是 Alpha 挖掘、树模型、门控，还是你说的 HMM 状态加权，都会把噪音当信息学进去。

下面我按“先诊断，再给修改方案，再给整体稳健化建议”的方式详细展开。

## 一、先说总判断：现在的主要问题不是“要不要再 clip 一下”，而是“有些字段的定义本身就需要重做”

你在 registry 里已经把 40 个特征按 A/B/C/D/E 域拆开了，处理意图也写得很明确，比如 A 域是量价，B 域是资金流，C 域是筹码，E 域是日内摘要；domain registry 里也标了哪些字段本来就该做 winsorize、哪些是 log、哪些是 clipped。这个框架本身是好的，说明你已经在按“域数据场”思考而不是乱堆大宽表。

但是，当前 JSON 里几个异常值区间说明：**现在的问题并不主要出在“剪尾力度不够”，而是公式定义、分母锚点、边界保护和 merge/覆盖率逻辑本身不稳**。最明显的例子有这些：

- `ret_oc_1d` 最大值到 `1279.0`，作为开到收收益率，这几乎可以判定不是正常金融分布，而是 `open≈0` 或脏值穿透导致。
- `lower_shadow_ratio` 最小值到 `-22000026.7`，这不是简单异常值，而是 K 线几何关系被破坏、或 `high-low≈0` 时被 epsilon 强行放大导致。
- `vwap_close_bias_1h` 最小值到 `-971.79`，如果定义真是 `(close-vwap_1h)/close`，这种量级基本只能来自 `close≈0` 或分母不应取 `close`。
- `volume_concentration_pm` 最小值到 `-2.0958`，但按“下午成交量占比”理解，本应在 `[0,1]`，这说明不是 share，而是源数据或公式定义出现偏差。
- `chip_width_85_15` 最大到 `31.51`，`close_vs_cost50` 最小到 `-18.86`，`support_5` 最小到 `-5.56`，这些都说明筹码类分母用 `close` 时，低价边界或脏价格会把比值炸穿。
- `raw_daily` 里 `open/high/low/pre_close/change/pct_chg/vol/amount` 的缺失率都在约 `0.4985`，但 `close` 却是 `0.0` 缺失，这个高度同步的 49.85% 缺失，不像自然缺失，更像**系统性 join/覆盖区间错误**。

这些都说明：你现在最该做的不是“在现有特征上再加一层 zscore”，而是把**公式、分母、边界、缺失逻辑**重新梳理一遍。

## 二、当前 JSON 里最严重的值问题，按严重程度分四层

***

### 1）第一层：强烈怀疑存在系统性对齐或 merge 错误

最可疑的是 A 域和 `raw_daily` 的同步缺失。

在 `feature_A_price_volume` 里，`ret_cc_1d`、`gap_open`、`intraday_range` 的缺失率都在 `0.4985` 左右，`ret_oc_1d`、上下影线也差不多；`raw_daily` 里 `open/high/low/pre_close/change/pct_chg/vol/amount` 也是同样比例缺失，但 `close` 却完全不缺。这个模式非常不自然。正常情况下，如果原始日线真的大面积缺失，`close` 不可能独自完好；如果是上市前样本扩张，`close` 也不该独自完整。

这通常意味着三种可能：

第一种，`close` 来自一张基表，而 `open/high/low/pre_close/...` 来自另一张表，merge key 或时间覆盖不一致。\
第二种，你构特征时用的是某个“全市场全日历面板”，但 `daily.parquet` 只覆盖一部分股票/时段，导致一半行对不上。\
第三种，`close` 在主表中被提前填充或保留，而其他列保持空值，于是衍生特征跟着成片缺失。

这个问题的关键在于：**这不是可接受的“自然缺失”，而是应该先修复的“结构性缺失”**。\
如果你后面直接 `ffill` 或 `fillna(0)`，就会把系统错误伪装成有意义样本。

#### 我建议的处理

- 先按 `(ts_code, trade_date)` 对 `raw_daily` 回溯检查：\
  只要 `close` 非空但 `open/high/low/pre_close` 成片为空，就视为上游 merge bug，不做普通填充。
- 增加完整性规则：\
  `close` 非空时，`open/high/low/pre_close` 至少应满足“同源覆盖率阈值”；否则该行整组 A 域特征禁用。
- 对 A 域新增一个 `a_domain_valid_flag`：\
  只在 `open, high, low, pre_close, close` 全部满足基础合法性时才产出 A 域衍生特征。

这点非常重要。A 域不是“少数值脏”，而是看起来有**整块样本失配**。

***

### 2）第二层：分母锚点不稳，导致比率爆炸

这是这次 JSON 最大的问题。

你现在大量特征用的是“某个价差 / close”或“某个价差 / open”这类形式。从 registry 看，很多公式都写成了 `(...)/(close + eps)`、`close/open - 1`、`(close-vwap)/close` 这种结构。

这种写法在中高价股票上通常没问题，但只要底层价格接近极小值，或源数据存在 `0.01 / 0 / 错位价`，epsilon 就会把“应该判 invalid 的样本”变成“巨大的有限值”。你当前多个异常值都属于这个范畴。

#### 典型例子 1：`ret_oc_1d`

定义是 `close/open - 1`，最大值 `1279.0`。如果 `open=0.01` 而 `close` 是十几元，这个数就会直接炸穿。

#### 典型例子 2：`close_vs_cost50`

定义是 `(close-cost_50pct)/(close+eps)`，最小值 `-18.86`。这说明某些行里 `close` 极小，而 `cost_50pct` 正常。这个分母逻辑不稳。

#### 典型例子 3：`vwap_close_bias_1h`

registry 里写的是 `(close - vwap_1h)/close`，JSON 最小值 `-971.79`。本质还是同一类问题。

#### 典型例子 4：`chip_width_85_15`

定义是 `(cost_85pct-cost_15pct)/close`，最大 `31.51`。只要 `close` 被脏值压到很小，分布宽度就会看起来极端巨大，但这并不代表筹码真实极端。

#### 应该怎么改

核心原则是：**分母要用“语义上稳定、数值上不贴零、且与分子同尺度”的锚点。**

我建议改成下面这套：

- 价格差异类，不要优先除以 `close`，改成除以更稳的中心价：\
  `price_anchor = max(abs(cost_50pct), abs(weight_avg), abs(pre_close), price_floor)`\
  或者对筹码域直接除以 `cost_50pct` / `weight_avg`。
- 收益率类，对 `open`、`pre_close`、`vwap` 这类分母，必须做**有效分母门槛**，不是简单 `+1e-8`：
  - 若 `abs(denominator) < floor`，直接记为 `NaN`
  - 不要强行算出一个巨大有限值
- 宽度类，如 `chip_width_95_5`、`chip_width_85_15`，建议改成\
  `(...)/max(cost_50pct, price_floor)`\
  而不是 `(...)/close`

更具体一点：

- `close_vs_cost50`\
  从 `(close-cost_50)/(close+eps)`\
  改为 `(close-cost_50)/max(cost_50, price_floor)`
- `close_vs_weight_avg`\
  改为 `(close-weight_avg)/max(weight_avg, price_floor)`
- `chip_width_95_5`\
  改为 `(cost_95-cost_5)/max(cost_50, price_floor)`
- `chip_width_85_15`\
  改为 `(cost_85-cost_15)/max(cost_50, price_floor)`
- `overhang_95`\
  改为 `(cost_95-close)/max(cost_95, close, price_floor)` 或 `/max(cost_50, price_floor)`
- `support_5`\
  改为 `(close-cost_5)/max(cost_5, close, price_floor)`
- `vwap_close_bias_1h`\
  改为 `(close-vwap_1h)/max(vwap_1h, close, price_floor)`

这里的 `price_floor` 不应是 `1e-8`，而应是**业务层面的可交易价格地板**。A 股历史里我建议至少用 `0.05` 或 `0.1`，更稳一点可以 `0.5`，然后把低于地板的样本直接记为 invalid。因为这种样本本来就是你不应该用来学习正常横截面关系的。

### 3）第三层：本应有自然边界的变量越界，说明公式或源数据口径不一致

有几类变量从定义上就应该落在固定区间，现在却越界了。

#### `lower_shadow_ratio`

理论上应该在 `[0,1]`，但你这里最小值到了 `-22000026.7`。registry 里公式是\
`(min(open,close)-low)/(high-low+epsilon)`。

如果 OHLC 合法，分子分母都应非负，结果不可能是巨大负数。出现这个值几乎只可能来自：

- `low > min(open, close)`，K 线数据本身不合法；
- `high < low` 或 `high-low≈0`；
- 分母几乎为 0，但分子因脏值变成负数；
- 公式计算前 OHLC 未做一致性校验。

#### `upper_shadow_ratio`

目前区间 `[0,1]` 看起来正常，但和 `lower_shadow_ratio` 对称，说明上影的运气好，不代表逻辑稳。

#### `volume_concentration_pm`

定义是“下午成交量占比”，本应在 `[0,1]`，现在最小值是 `-2.0958`。这表明：

- 要么 `vol_pm` 本身可能为负或来自差分错误；
- 要么 `vol_total` 过小或为负；
- 要么该字段其实不是 share，而 metadata 描述写错。

#### `price_pos_hist` 与 `winner_rate_pct`

这两个当前都在 `[0,1]`，说明你对这两个字段的边界处理是合理的。尤其 `winner_rate_pct` 已经把原始 `winner_rate` 从 `[0,100.56]` 归一到 `[0,1]`，这是好的；前一版原始数据里 `winner_rate` 的确超过 100，归一后 clip 到 `[0,1]` 是正确的。

#### 我建议的处理

所有“几何比例”和“天然份额比例”统一加**业务边界断言**：

- `upper_shadow_ratio`, `lower_shadow_ratio`, `price_pos_hist`, `winner_rate_pct`, `large_buy_share`, `large_sell_share`, `volume_concentration_pm`\
  都要先 `assert` 合法公式条件，再 `clip` 到理论边界。
- 一旦原始输入破坏边界条件，不要只 clip，先产出 `invalid_flag`，并记录日志。
- 对 `volume_concentration_pm`，如果它真的是 share，就必须重算并强制 `[0,1]`；如果不是 share，要改字段名，避免误导模型。

### 4）第四层：元数据与统计输出本身也有异常信号

`lasthour_ret` 的 `value_range` 上界是 `null`，这通常说明统计过程本身在 max 计算时遇到了空列、全 NaN、或类型混乱。

这说明你现在不仅要修特征，还要修**元数据生成器**，至少要保证：

- range 统计前统一替换 `inf/-inf`
- 只在有效值样本上算 min/max
- 若全空，则显式标记 `all_missing=true`
- 若列有混合 dtype，要先规范

这个问题虽然不像爆值那样直接伤模型，但它是个很好的信号：**你的特征产出层和元数据审计层要一起做稳。**

## 三、结合 `utils_clean.py`，现在的清洗工具为什么不够稳

这次我觉得真正值得你马上改的，不只是某几个特征公式，还有 `utils_clean.py` 的思路。因为你后面一旦把它作为统一工具库复用，问题会被系统性放大。

***

### 1）`safe_div` 现在不是真正的 safe

现在是：

```
return numerator / (denominator + epsilon)

```

这只能避免 Python 层面的除零报错，但**不能避免业务层面的假大值**。

在金融特征里，真正稳健的除法应该区分三种情况：

- 分母为 0 或接近 0：直接 `NaN`
- 分母无意义但有业务替代锚点：改用替代锚点
- 分母可用：正常计算

所以这里建议重写成“带有效分母门槛和可选裁剪”的版本，而不是一律 `+epsilon`。

***

### 2）`fill_missing(..., method='ffill')` 有面板串股风险

现在函数直接 `series.ffill()`，如果你在全表排序后直接对列调用，前一只股票最后一行会把值传给下一只股票第一行，这是非常严重的面板泄露。

这类函数必须至少支持：

- 按 `ts_code` 分组再 `ffill`
- 可限制 `limit`
- 可选是否只补单日断点
- 明确不跨停牌/跨上市前/跨退市后

你 registry 里对筹码类已经写了 `ffill_1d_if_single_gap`，这个意图是对的，但当前工具函数根本还不支持这么细的逻辑。

***

### 3）`clip_outliers` / `winsorize_series` 现在是“全局截尾”，不适合你的横截面任务

现在是直接对整列算 quantile，这会把不同年份、不同市场状态、不同股票生命周期的分布混在一起。

对你这种截面因子研究，更合理的是：

- **横截面日内 winsorize**：按 `trade_date`
- 或者 **行业内日内 winsorize**：按 `trade_date + industry`
- 对时间序列模型则做股票内 rolling robust scaling

全局截尾不是不能用，但只能作为最后兜底，不应是主处理。

***

### 4）`check_infinity` 只处理 inf，不处理“巨大的有限异常值”

你现在很多问题恰恰不是 `inf`，而是像 `1279`、`-971`、`-22000026` 这种“有限但无意义”的值。`check_infinity` 抓不到。

所以要新增：

- 业务边界检查
- 公式一致性检查
- 极端有限值告警
- 分母有效性检查

***

## 四、我建议你逐字段怎么改，按域给出具体方案

***

### A 域：价格量能特征

当前 registry 中 A 域的处理里，`ret_cc_1d`、`gap_open`、`intraday_range` 做了 `clip_1_99`，`volume_ratio_ln` 做了 log，影线比没有 clip。

#### 1. `ret_cc_1d`

这个字段区间看起来正常，问题主要在高缺失。\
建议：

- 不填充；
- 若 `pre_close <= price_floor` 或缺失，直接置 `NaN`
- 缺失来源先排查 merge，不要直接认为自然缺失。

#### 2. `ret_oc_1d`

必须加分母门槛。\
建议：

- `open <= price_floor` 时设为 `NaN`
- 然后做截面 winsorize，不做全局 winsorize
- 可再加一个硬边界，如 `[-0.5, 0.5]` 或更宽，看你是否保留极端事件

#### 3. `gap_open`

逻辑和 `ret_cc_1d` 类似。\
建议：

- `pre_close <= price_floor` 时 invalid
- 与涨跌停、停牌状态联动过滤

#### 4. `intraday_range`

公式是 `(high-low)/(pre_close+eps)`，这里分母建议改成 `max(pre_close, open, close, price_floor)` 中更稳的锚点之一，且要先检查 `high>=low`。\
若 `high<low`，整行 K 线无效。

#### 5. `upper_shadow_ratio` / `lower_shadow_ratio`

应先检查：

- `high >= max(open, close)`
- `low <= min(open, close)`
- `high > low + range_floor`

若不满足，先标 invalid，不要直接算。\
之后结果强制 clip 到 `[0,1]`。\
尤其 `lower_shadow_ratio` 当前必须重算。

#### 6. `turnover_free`

目前范围 `[0, 56]`，从含义看可以接受，但右尾偏重。\
建议：

- 保留原值
- 可在模型输入阶段做 `log1p` 版本并保留原版
- 中性化可选，不建议在特征层强做

#### 7. `volume_ratio_ln`

这个字段目前看起来比较稳，是 A 域处理里做得比较好的一项。\
但要确认原始 `volume_ratio` 是否为负或脏值，log 前要 `max(x, 0)`。

***

### B 域：资金流特征

B 域整体比 A 域稳。几个 imbalance 本身在 `[-1,1]`，`large_buy_share`、`large_sell_share` 在 `[0,1]`，`flow_divergence` 在 `[-2,2]`，这些都合理。

这说明 B 域的相对量构造基本成功。

#### 但仍有两个要改的点：

#### 1. `net_mf_to_amount`

notes 里已经写了 “Note unit conversion needed”，这是个重要提醒。\
如果 `net_mf_amount` 和 `amount` 单位不一致，这个比值虽然当前范围看起来正常，也可能只是“碰巧被压在一个区间里”。

建议：

- 先统一单位，再计算
- 当 `amount <= amount_floor` 时置 `NaN`
- 不要因为 B 域缺失率低就一律 fill 0

#### 2. `zero_if_both_zero_else_nan`

这个 fill policy 的方向是对的。\
但建议进一步明确：

- 若买卖都为 0 且当日成交额为 0，可设 0
- 若买卖都为 0 但总成交正常，视为上游异常，应设 `NaN + flag`
- 若任一边缺失，不要自动按 0 处理

总体而言，B 域是目前最接近“可直接进模型”的一组。

***

### C 域：筹码特征

C 域是你后面很值得重视的域，但也是这次值问题最集中的域之一。它的问题不是概念错，而是**相对化的锚点选得不够稳**。

#### 1. `close_vs_cost50`

当前公式 `(close - cost_50pct) / (close + eps)` 不建议继续用。\
建议改成：

- `(close - cost_50pct) / max(cost_50pct, price_floor)`

原因：成本中位本来就是这个关系的自然锚点，用它比用 `close` 稳得多。

#### 2. `close_vs_weight_avg`

同理，改成：

- `(close - weight_avg) / max(weight_avg, price_floor)`

#### 3. `chip_width_95_5`, `chip_width_85_15`

建议都改成除以 `cost_50pct` 或 `weight_avg`，不要再除 `close`。\
这样得到的宽度才更像“成本分布相对宽度”。

#### 4. `overhang_95`, `support_5`

这两个可以保留“压力/支撑”的思想，但分母改成成本锚点。\
另外这两个字段都可以再做一版 clip，比如 `clip_0.5_99.5` 或 hard clip。

#### 5. `winner_rate_pct`

当前做得好。建议保留。\
但要保留原始 `winner_rate` 作为 QA 对照，不直接进模型。前一版原始元数据里 `winner_rate` 上界超过 100，说明供应商层面会有轻微越界，clip 到 `[0,1]` 是必要的。

#### 6. `price_pos_hist`

当前 `[0,1]` 合理，但要额外检查：

- `his_high >= his_low`
- `close` 在合理范围内
- 若 `his_high == his_low`，应置 `NaN` 或给中性值，不要直接靠 epsilon

#### 7. 缺失填充

registry 里写的是 `ffill_1d_if_single_gap`，这个策略我赞成。\
但前提是：

- 必须按 `ts_code` 分组
- 只补单日小断点
- 不跨停牌长区间
- 不跨上市前期
- 补完保留 `filled_flag`

***

### E 域：日内摘要特征

E 域是另一个“思路对，但几项要重写”的区域。

#### 1. `hour1_ret`

范围正常，缺失率很低，可保留。\
但建议加分母门槛。

#### 2. `lasthour_ret`

上界是 `null`，先修 metadata 统计，再检查原列是否有全空子样本。\
处理前先 `check_infinity + finite-only summary`。

#### 3. `midday_reversal`

## 五、我会怎么重写 `utils_clean.py`

你这次不是单纯问分析，所以我直接给你“应该改成什么思路”。

### 1）把 `safe_div` 改成“有效分母除法”

现在的 `safe_div` 太弱。\
你需要的是这种逻辑：

- 支持 `min_abs_denominator`
- 支持 `invalid_to_nan`
- 支持 `hard_clip`
- 支持传入 `valid_mask`

伪逻辑：

```
def safe_div_strict(num, den, min_abs_den=1e-4, fill_value=np.nan):
    den = den.astype(float)
    out = pd.Series(np.nan, index=num.index)
    valid = den.notna() & np.isfinite(den) & (den.abs() >= min_abs_den)
    out.loc[valid] = num.loc[valid] / den.loc[valid]
    return out

```

但对价格类分母，不建议 `1e-4` 这种数学阈值，而要用业务阈值，比如 `0.05/0.1/0.5`。

***

### 2）把 `fill_missing` 改成分组版，禁止串股

### 3）新增“边界断言 + 公式合法性检查”

例如：

- OHLC 合法性：

## 七、结合你此前的整体思路，我建议把这次修改落实成一套“稳健预处理制度”

你之前已经非常清楚地提出：原始数据必须留存、域数据要拆分、不要为了语法把数据处理做乱、先把 Feature Registry 做好，再往 Alpha 挖掘和模型层推进。这个思路我还是完全赞成。

这次这份 JSON 暴露出来的问题，恰好说明你那个大方向是对的。因为现在最需要的不是扩充更多因子，而是把域内预处理制度真正定下来。

我建议你把数据处理流程定成下面这 8 步：

### 第 1 步：Raw 保留

原始下载数据永不覆盖，只增不改。\
这点你前面已经明确过，很对。

### 第 2 步：Canonical 校验

统一主键、日期、单位、交易日对齐。\
这里修掉 `raw_daily` 那种系统性缺失。

### 第 3 步：输入合法性检查

先检查 OHLC、筹码单调、时间合法，再算衍生特征。

### 第 4 步：严格分母逻辑

凡是 ratio，都先检查 denominator validity，而不是统一 `+1e-8`。

### 第 5 步：域内特征重算

把 A/C/E 域的问题字段按上面的建议重算。

### 第 6 步：域内 QA 日志

记录 invalid、fill、clip、drop。

### 第 7 步：面向任务的标准化

- 横截面任务：按日 winsorize / robust zscore / group rank
- 时序任务：股票内 rolling scaling

### 第 8 步：模型层再做中性化与组合

行业中性化、group rank、门控、HMM、LGBM 这些放在后面，不拿它们去掩盖前面数据层的问题。\
你之前已经判断“在因子挖掘阶段追求可解释、低维、互补；模型阶段追求非线性与交互”，这次我认为这个判断再次被数据验证了。
